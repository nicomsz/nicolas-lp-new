System design com um gateway de LLM

Os conceitos de arquitetura que aparecem quando um produto usa LLM em produção, explicados com o código e os números de um projeto que roda: o llm-gateway.

O que é um gateway de LLM

É um servidor que fica entre os seus apps e as APIs dos modelos (Anthropic, OpenAI e outras). Os apps chamam o gateway no lugar do provedor, e o gateway resolve num lugar só o que todo app com LLM acaba precisando.

Sem gateway, cada serviço chama a API do modelo direto, com a chave real:

Com o gateway, o serviço troca só o endereço e a chave. O resto do código continua igual, porque o gateway fala o mesmo formato da API:

Os problemas que ele resolve

O provedor fica fora do ar
A API do modelo devolve erro de sobrecarga por 20 minutos, e o seu produto cai junto. O gateway troca de provedor sozinho.
Um cliente gasta a cota de todos
Um cliente dispara requests em loop e consome os tokens que eram de todos os outros. O gateway limita cada cliente separadamente.
Ninguém sabe quanto custa
Alguém pergunta "quanto o cliente X custou este mês?" e não tem como responder. O gateway registra tokens e custo de cada request.

Proxy reverso: o gateway no meio do caminho

Por que colocar um servidor a mais entre o app e o provedor, e quanto isso custa em latência.

Em uma frase

Um proxy reverso é um servidor que recebe os requests no lugar do servidor de verdade, decide o que fazer com cada um e repassa para quem responde. O gateway de LLM é um proxy reverso especializado em APIs de modelos.

Quando você precisa

Mais de um app usa LLM
Sem um ponto central, cada app reimplementa retry, limite e log do seu jeito, e cada um tem uma cópia da chave real da API.
A chave não pode vazar
O app recebe uma chave do gateway (gw_acme_123). A chave real do provedor fica só no gateway. Se a chave do app vazar, você revoga só ela.
Você precisa trocar de provedor
Com o gateway, mudar de provedor ou somar um segundo é mudança de configuração num lugar só, sem deploy dos apps.

Por que é a escolha comum

A alternativa é uma biblioteca compartilhada, instalada em cada app. Ela resolve retry e log, mas não resolve o que depende de estado compartilhado: a cota de um tenant precisa ser contada num lugar só, mesmo que ele use três apps. A biblioteca também espalha a chave real por todos os apps, e uma correção nela exige atualizar e publicar cada app de novo.

O custo do gateway é um salto de rede a mais e um ponto a mais que pode cair. Por isso ele precisa ser leve (o experimento abaixo mede isso) e rodar em mais de uma cópia.

Como funciona

  1. O app manda POST /v1/messages para o gateway, com a chave do tenant no header x-api-key.
  2. O gateway procura a chave na lista de tenants. Se não achar, responde 401 e para ali.
  3. Ele passa pelas outras paradas (cache, rate limit, balanceador) e chama o provedor escolhido, agora com a chave real.
  4. A resposta do provedor volta para o app sem alteração. O gateway só acrescenta headers próprios, como x-gateway-upstream, que diz qual provedor respondeu.
  5. No fim, o gateway grava uma linha de log com o tenant, o provedor, a latência, os tokens e o custo.

Object.hasOwn e não config.tenants[key] direto: com o acesso direto, a chave "constructor" acharia uma função herdada do Object e passaria como tenant.

O que o experimento mostrou

2.000 requests, 20 ao mesmo tempo, para um provedor falso que responde em 100 ms. Primeiro direto, depois pelo gateway.

Caminhop50p99Requests por segundo

O gateway acrescentou 1 ms na mediana e 6 ms no p99. Perto de uma chamada de LLM, que leva de centenas de milissegundos a vários segundos, é ruído.

Pergunta de entrevista

O gateway não vira um ponto único de falha?

Vira, se rodar uma cópia só. Por isso ele roda em várias cópias atrás de um load balancer comum, e o estado que precisa ser compartilhado (a cota dos tenants e o cache) fica no Redis, não na memória de cada cópia. A lição 3 mostra o que acontece quando o próprio Redis cai.

Streaming, backpressure e cancelamento

Como repassar a resposta aos pedaços sem segurar nada, sem estourar a memória e sem pagar por texto que ninguém vai ler.

Em uma frase

Com streaming, o provedor manda a resposta em pedaços enquanto o modelo gera, e o gateway repassa cada pedaço para o app assim que ele chega.

Quando você precisa

Chat com o usuário esperando
Uma resposta longa leva 10 segundos para ficar pronta. Com streaming, o texto começa a aparecer em menos de 1 segundo. O tempo total é o mesmo; o que muda é quando o usuário vê o primeiro pedaço (o TTFT).
O usuário fecha a aba
O modelo continua gerando texto, e você continua pagando por ele, a menos que alguém avise o provedor que ninguém está mais lendo.
O cliente está numa rede lenta
O provedor manda mais rápido do que o celular do cliente consegue receber. Sem controle, o gateway acumula o excesso na memória.

Por que é a escolha comum

A API de mensagens usa SSE (Server-Sent Events): a resposta é um HTTP comum, com content-type: text/event-stream, que não termina até o último evento. Comparado a WebSocket, SSE é HTTP comum: usa os mesmos headers, a mesma autenticação e as mesmas ferramentas de qualquer request, e o fluxo só vai do servidor para o cliente, que é exatamente o caso de uma resposta de modelo.

O gateway não monta a resposta inteira antes de repassar. Se montasse, o TTFT do app seria o tempo total da resposta, e o streaming do provedor não serviria para nada.

Como funciona

O que trafega na conexão é texto, um evento por bloco, separado por linha em branco:

O gateway faz três coisas com esse fluxo, ao mesmo tempo:

  1. Repassa cada pedaço para o app assim que chega, sem esperar o próximo.
  2. Lê os eventos no caminho, para saber quantos tokens foram usados (message_start traz a entrada, message_delta traz a saída acumulada) e calcular o custo.
  3. Respeita o ritmo do cliente: res.write() devolve false quando o buffer de saída para o cliente encheu. Aí o gateway para de ler do provedor até o evento drain, que avisa que o buffer esvaziou. Isso é backpressure: quem recebe mais devagar controla a velocidade de quem manda.

E o cancelamento: quando o app fecha a conexão antes do fim, o gateway cancela a chamada ao provedor com um AbortController. A conexão com o provedor fecha, e ele para de gerar.

O que o experimento mostrou

Um provedor que manda o primeiro pedaço em 200 ms e depois 20 pedaços, um a cada 50 ms. 300 requests, 20 ao mesmo tempo.

CaminhoPrimeiro pedaço, p50Primeiro pedaço, p99Resposta completa, p50
Direto no provedor202 ms207 ms1.208 ms
Pelo gateway203 ms221 ms1.208 ms

O primeiro pedaço chega pelo gateway 1 ms depois de chegar direto. Se o gateway montasse a resposta antes de repassar, esse número seria 1.208 ms.

No teste de cancelamento, 100 clientes fecharam a conexão 400 ms depois de enviar. Os 100 cancelamentos chegaram ao provedor, que gerou 429 dos 2.000 pedaços que geraria: 21% do texto, e do custo.

Pergunta de entrevista

Por que o gateway não guarda a resposta inteira e manda de uma vez?

Porque o TTFT do app viraria o tempo total da resposta, e a memória do gateway cresceria com o tamanho de cada resposta vezes o número de requests em andamento. Repassando pedaço por pedaço, com backpressure, cada request ocupa no máximo o tamanho de um buffer.

Rate limit por tokens

Como impedir que um tenant gaste a capacidade de todos, contando o que realmente custa: tokens, e não requests.

Em uma frase

Rate limit é o limite de quanto cada tenant pode consumir por unidade de tempo. Aqui ele é contado em tokens do modelo, com o algoritmo token bucket.

Quando você precisa

Um tenant com bug em loop
Um app entra em loop e manda 300 requests por segundo. Sem limite por tenant, ele ocupa a capacidade do provedor, e os outros tenants recebem erro.
Requests de tamanhos muito diferentes
Um request de 50 tokens e um de 50.000 custam valores muito diferentes. Um limite de "100 requests por minuto" deixa passar o caro e barra o barato.
Plano gratuito e plano pago
Cada tenant tem a sua cota. Mudar o plano de um cliente é mudar um número.

Por que é a escolha comum

O token bucket guarda só dois números por tenant: o saldo e a hora da última atualização. O saldo sobe numa taxa fixa até um teto, e cada request desconta dele. Comparado à janela fixa ("6.000 tokens por minuto, zerando no minuto cheio"), ele não deixa o tenant gastar a cota inteira no fim de um minuto e de novo no começo do seguinte. Comparado a guardar a hora de cada request (janela deslizante), ele usa memória constante.

O problema específico de LLM: só depois da resposta se sabe quantos tokens o request usou. A solução é reservar e devolver: na entrada, o gateway desconta uma estimativa (o tamanho do texto dividido por 4, mais o max_tokens pedido); no fim, devolve ao saldo o que não foi usado.

Como funciona

Exemplo com uma cota de 6.000 tokens por minuto, ou seja, 100 tokens por segundo de recarga:

  1. O tenant chega com saldo cheio: 6.000.
  2. Um request estima 1.200 tokens. O saldo cai para 4.800, e o request passa.
  3. A resposta usou só 300. O gateway devolve 900: o saldo vai para 5.700.
  4. Se um request estimar mais do que o saldo, o gateway responde 429 com o header retry-after: quantos segundos faltam para a recarga cobrir a diferença.

Com várias cópias do gateway, o saldo precisa ficar num lugar só: o Redis. Mas "ler o saldo, calcular, gravar" em três comandos separados tem uma corrida: duas cópias leem o mesmo saldo de 1.000, as duas descontam 800, e as duas deixam passar. Por isso a conta roda num script Lua dentro do Redis, que executa o script inteiro antes de atender qualquer outro comando.

E se o Redis cair? O gateway deixa o request passar (fail open): fica sem limite por um tempo em vez de derrubar todos os tenants junto com o Redis. Para um sistema em que estourar a cota custa mais caro do que ficar fora do ar, a escolha certa seria o contrário (fail closed).

Pergunta de entrevista

Por que contar tokens, e não requests?

Porque o custo e a carga de um request de LLM variam centenas de vezes com o tamanho do texto. Limite por request trata igual o barato e o caro. O detalhe que mostra que você entendeu: o custo real só é conhecido no fim, então você reserva uma estimativa na entrada e devolve a diferença na saída.

Balanceamento de carga

Como escolher o provedor de cada request, e por que a estratégia "mais esperta" foi a que mais errou quando um provedor caiu.

Em uma frase

Balanceamento de carga é a regra que decide para qual dos provedores disponíveis vai cada request.

Quando você precisa

Mais de uma conta ou região
Cada conta de API tem o seu limite de requests por minuto. Duas contas, ou a mesma API em duas regiões, somam capacidade, desde que o tráfego seja dividido entre elas.
Provedores com velocidades diferentes
Um provedor está mais lento hoje. Mandar para ele a mesma quantidade que para os outros acumula requests esperando nele.

Por que é a escolha comum

As duas estratégias mais usadas, e as duas que o projeto implementa:

  • Rodízio (round-robin): um para cada, em ordem. Não precisa de nenhuma informação sobre os provedores e divide igual.
  • Menos ocupado (least-in-flight): manda para o provedor com menos requests em andamento. Se adapta sozinho a um provedor mais lento, porque os requests dele demoram a terminar e o contador dele fica alto.

"Menos ocupado" costuma ser a melhor escolha quando os tempos de resposta variam muito, que é o caso de LLM: um request pode levar 200 ms e o seguinte 30 segundos.

Como funciona

A carga de um provedor é quantos requests estão em andamento nele mais quantos esperam na fila dele. No empate, vale a ordem do rodízio, para não mandar tudo para o primeiro da lista.

O que o experimento mostrou

Três provedores de 100 ms; um deles devolvendo erro 529 (sobrecarregado) em tudo. 150 requests por segundo durante 8 segundos, sem nenhuma nova tentativa.

EstratégiaErrosChamadas ao provedor caído
Rodízio33,3%400 de 1.200
Menos ocupado87,2%1.046 de 1.200

O rodízio errou exatamente 1 de cada 3, como esperado. O "menos ocupado" errou quase tudo. O motivo: o provedor caído responde o erro quase na hora, então ele quase nunca tem request em andamento. Para o balanceador, ele é sempre o mais livre, e recebe quase tudo.

A lição: "menos ocupado" mede a fila, não a saúde. Um provedor que falha rápido parece ótimo. Quem resolve isso é o circuit breaker (lição 6), que tira o provedor doente da lista de candidatos.

Pergunta de entrevista

Least connections é sempre melhor que round-robin?

Não. Ele se adapta a provedores lentos, mas um provedor que devolve erro rápido fica com zero conexões e passa a receber todo o tráfego. Ele precisa vir junto com health check ou circuit breaker, que tiram o provedor doente da escolha.

Failover, retry e backoff

Quando vale tentar de novo em outro provedor, quanto esperar antes, e o momento em que não dá mais para trocar.

Em uma frase

Failover é tentar o mesmo request em outro provedor quando o primeiro falha; backoff é a espera entre uma tentativa e a próxima.

Quando você precisa

O provedor está sobrecarregado
A API devolve 529 (sobrecarga) ou 503. Outro provedor, ou o mesmo uns segundos depois, provavelmente responde.
A conexão caiu no meio do caminho
A rede falhou antes da resposta chegar. O request não chegou a ser processado, ou foi processado e a resposta se perdeu; tentar de novo resolve os dois casos para uma pergunta ao modelo.

Por que é a escolha comum

Nem todo erro merece nova tentativa. A regra do projeto:

ResultadoTenta de novo?Por quê
Falha de conexão, tempo limiteSimProblema no caminho ou no provedor
429, 529, 500 a 504SimO provedor está sobrecarregado ou com defeito
400, 401, 404NãoO problema é o request: outro provedor daria a mesma resposta

E a espera entre tentativas dobra a cada falha, até um teto, multiplicada por um número aleatório entre 0 e 1. Esse número aleatório é o jitter: sem ele, 1.000 requests que falharam no mesmo segundo tentam de novo todos no mesmo instante e derrubam o provedor que estava se recuperando.

Como funciona

  1. O gateway escolhe um provedor entre os que ainda não foram tentados neste request.
  2. Se ele falhar com um erro que vale nova tentativa, o gateway espera o backoff e escolhe outro.
  3. Há um prazo total por request. Se a próxima espera passar do prazo, o gateway desiste e devolve o último erro.
  4. A regra do primeiro byte: no streaming, depois que o primeiro pedaço foi enviado ao app, não existe mais troca de provedor. O app já mostrou parte do texto; começar de novo em outro provedor duplicaria a resposta. Se o provedor falhar no meio, o app recebe um evento de erro no próprio stream.

O que o experimento mostrou

O mesmo cenário da lição 4: três provedores, um devolvendo 529 em tudo.

ConfiguraçãoErrosp50p99Chamadas ao caído
Menos ocupado, sem failover87,2%104 ms126 ms1.046

O failover zerou os erros, mas a mediana dobrou. Quase todo request (1.196 de 1.200) ainda tentou primeiro o provedor caído, levou o erro e esperou o backoff (até 200 ms, em média 100 ms) antes de ir para um provedor bom. Failover sozinho troca erro por latência. A lição 6 mostra como recuperar a latência.

Pergunta de entrevista

Por que jitter no backoff?

Porque falhas chegam em grupo. Sem jitter, todos os clientes que falharam juntos esperam o mesmo tempo e tentam de novo no mesmo instante, criando um pico que pode derrubar o servidor de novo (o efeito manada, ou thundering herd). O número aleatório espalha as novas tentativas no tempo.

Circuit breaker

Parar de chamar um provedor que está falhando, e testar de tempos em tempos se ele voltou.

Em uma frase

O circuit breaker conta as falhas seguidas de um provedor; passou de um limite, o gateway para de mandar requests para ele por um tempo.

Quando você precisa

O provedor devolve erro
Cada request ainda tenta o provedor caído antes de ir para outro, e paga o erro mais a espera (lição 5).
O provedor trava sem responder
Pior que devolver erro: cada request que cai nele espera o tempo limite inteiro antes de desistir.
O provedor está tentando se recuperar
Continuar mandando tráfego para um serviço sobrecarregado atrasa a recuperação dele.

Por que é a escolha comum

A alternativa é um health check: chamar o provedor a cada X segundos para ver se está vivo. Ele demora até X segundos para perceber a queda e testa um endpoint de saúde, não o caminho real. O circuit breaker usa os próprios requests como sinal: percebe a falha no quinto erro seguido, sem tráfego extra.

Como funciona

Três estados por provedor:

EstadoO que aconteceMuda quando
FechadoRequests passam; o breaker conta as falhas seguidas5 falhas seguidas: vai para aberto
AbertoNenhum request vai para o provedorPassou o tempo de espera (2 s no experimento): vai para meio-aberto
Meio-abertoPassa 1 request de testeSucesso: fechado. Falha: aberto de novo

Um detalhe que importa: só conta como falha o que é culpa do provedor (erro 5xx, tempo limite, conexão perdida). Um 400 é culpa do request, e um 429 é a cota: abrir o circuito por causa deles tiraria do ar um provedor saudável.

Pergunta de entrevista

Com várias cópias do gateway, o estado do breaker deveria ficar no Redis?

Aqui ele fica na memória de cada cópia, e isso é uma escolha. Cada cópia descobre a queda sozinha, depois de 5 falhas dela; com 10 cópias, são 50 requests ruins em vez de 5. Em troca, o caminho do request não depende do Redis para decidir, e uma cópia com problema de rede não abre o circuito para todas.

Fila com limite e load shedding

Quantos requests cada provedor aguenta ao mesmo tempo, o que fazer com o excesso, e por que recusar rápido é melhor do que fazer esperar.

Em uma frase

Cada provedor tem um número máximo de requests em andamento; quem chega depois espera numa fila com tamanho e tempo máximos, e o que não cabe é recusado na hora (load shedding).

Quando você precisa

O provedor tem limite de concorrência
Sua conta aceita, digamos, 50 requests simultâneos. O 51º recebe erro do provedor. É melhor o gateway segurar o 51º um pouco do que gastar uma chamada com erro garantido.
Chega um pico maior do que a capacidade
Uma fila sem limite cresce sem parar, a espera cresce junto, e o app desiste (tempo limite) depois que o gateway já gastou trabalho com o request.

Por que é a escolha comum

Uma fila absorve picos curtos: 10 requests a mais por meio segundo esperam um pouco e passam. Mas sob excesso contínuo, uma fila só adia a falha. A regra que explica isso é a lei de Little: o número de itens num sistema é a taxa de chegada vezes o tempo que cada um fica lá.

Aplicada ao gateway: com 10 vagas e requests de 100 ms, o provedor atende no máximo 10 ÷ 0,1 s = 100 requests por segundo. Com 100 requests na fila, quem chega por último espera 100 ÷ 100 por segundo = 1 segundo antes de ser atendido. Uma fila de 10.000 seria uma espera de 100 segundos: ninguém espera isso. Por isso a fila tem tamanho e tempo máximos, e o excesso recebe 503 com retry-after imediatamente.

Como funciona

  1. Tem vaga livre? O request ocupa a vaga e segue.
  2. Não tem vaga, mas a fila tem espaço? O request espera na fila.
  3. A fila está cheia, ou o request esperou mais que o tempo máximo? Recusa com 503.
  4. Quando um request termina, a vaga passa direto para o primeiro da fila.

A função devolvida libera a vaga, e ela é chamada num bloco finally: com sucesso, com erro ou com o cliente indo embora, a vaga sempre volta. Uma vaga que não volta é um vazamento que só aparece depois de horas, quando todas estão presas.

O que o experimento mostrou

No teste do tenant barulhento (lição 3), o provedor tinha 10 vagas, fila de 100 e espera máxima de 3 s, e recebia 300 requests por segundo. Sem rate limit:

Requests do acme atendidos1.665
Mediana do beta, que só mandava 20 por segundo1.137 ms

Os 1.137 ms do beta são a lei de Little no número: cerca de 1 s de fila cheia mais os 100 ms do provedor. A fila protegeu o provedor, mas sozinha ela é justa com os requests, não com os tenants: quem manda mais ocupa mais a fila. Justiça entre tenants é trabalho do rate limit.

Pergunta de entrevista

Qual a diferença entre a fila e o rate limit, se os dois recusam requests?

O rate limit protege os tenants uns dos outros: é por tenant e olha o consumo ao longo do tempo. A fila protege o provedor: é por provedor e olha quantos requests estão em andamento agora. O experimento mostra os dois juntos: só a fila manteve o provedor de pé, mas só o rate limit devolveu o serviço ao beta.

Cache de respostas

Responder a mesma pergunta sem chamar o modelo de novo, sem misturar clientes e sem deixar 10 requests iguais virarem 10 chamadas.

Em uma frase

O cache guarda a resposta de um request por um tempo; o mesmo request, do mesmo tenant, recebe a resposta guardada sem ir ao provedor.

Quando você precisa

Perguntas que se repetem
Um assistente de FAQ recebe "qual o horário de atendimento?" centenas de vezes por dia, com a mesma configuração. Cada chamada custa tokens e leva segundos.
Um pico de requests iguais
Uma tela popular abre e 10 usuários disparam a mesma geração no mesmo segundo, antes da primeira terminar.

Por que é a escolha comum

Três decisões do projeto, cada uma contra um erro comum:

  • Só quando o cliente pede, pelo header x-gateway-cache: 60 (segundos de validade). Quem chama é que sabe se a resposta pode ser reaproveitada: uma FAQ pode, uma conversa com o contexto do usuário não pode.
  • O tenant faz parte da chave. A resposta de um tenant nunca é entregue a outro, mesmo que a pergunta seja idêntica.
  • Uma chamada para requests iguais simultâneos (single-flight). Sem isso, os 10 requests do pico chegam antes da primeira resposta existir, todos encontram o cache vazio, e todos vão ao provedor.

Como funciona

A chave do cache é um hash do tenant com o corpo do request, com as chaves do JSON em ordem alfabética: {"a":1,"b":2} e {"b":2,"a":1} são o mesmo request. O campo stream fica de fora, porque a resposta é a mesma; só muda o formato de entrega.

O single-flight é um mapa de chamadas em andamento: o primeiro request de uma chave registra uma Promise; os seguintes, em vez de chamar o provedor, esperam essa Promise.

Só entram no cache respostas completas e com sucesso. Um erro do provedor, ou um streaming cancelado no meio, não é guardado.

O que o experimento mostrou

1.000 requests, 10 ao mesmo tempo; 30% deles repetem uma de 10 perguntas frequentes. Esses 30% são uma premissa do teste, não um dado do mundo real.

ConfiguraçãoChamadas ao provedorRespostas do cacheCustoLatência média
Sem cache1.0000%US$ 0,159105 ms
Com cache68931,1%US$ 0,11073 ms

O cache respondeu 31,1%, praticamente toda a repetição que existia. O que o teste prova é que o mecanismo funciona sob concorrência; a economia real depende de quanto o seu tráfego se repete.

Pergunta de entrevista

O que é cache stampede e como evitar?

É quando uma entrada do cache não existe (ou expira) e muitos requests ao mesmo tempo vão buscar o mesmo valor na origem. Com LLM, cada busca é cara. A solução do projeto é single-flight: só o primeiro busca, os outros esperam o resultado dele.

Métricas e teste de carga

Como saber se cada mecanismo funciona: o que registrar de cada request, por que olhar o p99 e como gerar carga sem enganar a si mesmo.

Em uma frase

Observabilidade é conseguir responder perguntas sobre o sistema em produção a partir do que ele registra; teste de carga é gerar tráfego controlado para medir como ele se comporta.

Quando você precisa

Explicar a fatura
"Quanto o tenant X gastou este mês?" só tem resposta se cada request registrou o tenant, os tokens e o custo.
Decidir uma configuração
"5 falhas para abrir o circuito é muito ou pouco?" só tem resposta medindo o efeito.
Defender o projeto numa entrevista
"O circuit breaker baixou o p99 de 1.270 ms para 118 ms" vale mais do que "implementei um circuit breaker".

Por que é a escolha comum

Uma linha de log por request, em JSON (formato JSONL). Cada linha tem tudo sobre aquele request; qualquer pergunta vira um filtro e uma soma. É o formato que ferramentas como Datadog, Loki e BigQuery leem direto.

Percentis, não média. A média esconde a cauda: no experimento do provedor travado (lição 6), a mediana era 104 ms com e sem circuit breaker. Só o p99 mostrava que 138 requests passavam de 1 segundo. Um usuário que usa o produto o dia todo encontra o p99 várias vezes por dia.

Como funciona

O campo attempts guarda cada tentativa: um request que passou por failover mostra o provedor que falhou, o erro e o que respondeu.

No teste de carga, há dois jeitos de gerar tráfego, e eles respondem perguntas diferentes:

  • Concorrência fixa: N clientes, cada um manda o próximo request quando o anterior termina. Mede a vazão máxima. Se o sistema fica lento, os clientes mandam menos, e a carga cai junto: o teste alivia o sistema justamente quando ele piora.
  • Taxa fixa: um request a cada 1/taxa segundos, termine o anterior ou não. É como usuários de verdade chegam. Mostra a fila crescendo e a latência subindo sob excesso.

Os experimentos de queda e de tenant barulhento usam taxa fixa; os de custo do gateway e de cache usam concorrência fixa.

Pergunta de entrevista

Por que o teste de carga com N clientes fixos pode esconder um problema?

Porque cada cliente espera a resposta antes de mandar o próximo. Quando o sistema fica lento, a carga cai sozinha, e o teste nunca vê a fila crescer. Usuários reais não esperam os outros terminarem para chegar. Para medir comportamento sob excesso, a carga tem que ter taxa fixa.

Perguntas de entrevista

As perguntas que costumam aparecer sobre um sistema como este, com a resposta curta e a lição que explica cada uma.

Desenho geral

Desenhe um gateway para várias APIs de LLM.

Um proxy reverso com estas paradas, nesta ordem: autenticação, cache, rate limit por tenant, balanceador com circuit breaker, fila por provedor e a chamada com streaming. O estado compartilhado (cota e cache) fica no Redis; o resto, na memória de cada cópia. Uma linha de log por request. Lições 1 e 9.

Como escalar para várias cópias do gateway?

As cópias ficam atrás de um load balancer comum, sem estado próprio que importe entre requests. Cota e cache vão para o Redis, para todas verem o mesmo saldo e as mesmas respostas. O circuit breaker e a fila ficam por cópia, de propósito. Lições 3 e 6.

Limites e filas

Por que rate limit por tokens, e não por requests?

O custo de um request de LLM varia centenas de vezes com o tamanho do texto. O gateway reserva uma estimativa na entrada e devolve a diferença quando sabe o uso real. Lição 3.

O que acontece se o Redis cair?

O gateway deixa os requests passarem sem limite (fail open), em vez de derrubar todos os tenants. Se estourar a cota custasse mais do que ficar fora do ar, a escolha seria recusar (fail closed). Lição 3.

Como garantir que duas cópias não aprovem o mesmo saldo?

Ler, calcular e gravar o saldo num script Lua, que o Redis executa inteiro antes de atender outro comando. Três comandos separados teriam uma corrida entre as cópias. Lição 3.

Por que a fila tem tamanho máximo?

Pela lei de Little, a espera é o tamanho da fila dividido pela vazão. Uma fila sem limite sob excesso contínuo só faz a espera crescer até o cliente desistir. Melhor recusar com 503 na hora. Lição 7.

Falhas

Quais erros merecem nova tentativa?

Os do provedor: falha de conexão, tempo limite, 429, 529 e 5xx. Os do request (400, 401) não: outro provedor daria a mesma resposta. Lição 5.

Por que jitter no backoff?

Para que os clientes que falharam juntos não tentem de novo todos no mesmo instante e derrubem o servidor que está se recuperando. Lição 5.

Dá para trocar de provedor no meio de um streaming?

Não: o cliente já recebeu parte do texto, e recomeçar em outro provedor duplicaria a resposta. Depois do primeiro byte, uma falha vira um evento de erro no próprio stream. Lição 5.

Por que least-in-flight piorou com um provedor caído?

O provedor caído responde o erro quase na hora, então quase nunca tem request em andamento e sempre parece o mais livre. No experimento, os erros foram de 33,3% (rodízio) para 87,2%. Lição 4.

Circuit breaker ou health check?

O circuit breaker usa os próprios requests como sinal e percebe a queda na quinta falha seguida, sem tráfego extra; o health check testa um endpoint de saúde a cada intervalo. Os dois podem conviver. Lição 6.

Desempenho

O que é backpressure?

É quem recebe mais devagar controlar a velocidade de quem manda. No gateway: quando res.write() devolve false, ele para de ler do provedor até o evento drain. Lição 2.

Por que olhar o p99, e não a média?

A média esconde a cauda. Com um provedor travado, a mediana ficou em 104 ms com e sem circuit breaker; só o p99 (1.270 ms contra 118 ms) mostrou o problema. Lição 9.

O que é cache stampede?

Muitos requests buscando o mesmo valor ausente ao mesmo tempo. A solução é single-flight: só o primeiro vai ao provedor, os outros esperam a resposta dele. Lição 8.
